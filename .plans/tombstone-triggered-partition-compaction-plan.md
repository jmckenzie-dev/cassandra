# Tombstone-Triggered Partition Compaction Plan

## Goal

Goal: Enqueue a bounded, deduplicated, per-partition compaction when a local read crosses the tombstone warning threshold with tombstones that the read purge rules consider removable.

- Use a node-wide First In, First Out (FIFO) queue with a default capacity of 10 requests, including queued and active work. Reject excess requests without blocking read threads. A capacity of 0 disables new admissions. Support live changes through Java Management Extensions (JMX) and `system_views.settings`.
- Count each partition independently. A range read can enqueue each partition that exceeds `tombstone_warn_threshold`.
- Run accepted work on one dedicated compaction thread. Keep regular compaction and manual partition-compaction behavior unchanged.
- Do not bypass `gc_grace_seconds`, repaired-data restrictions, overlap checks, or active repair work.
- Log a rate-limited warning when Cassandra accepts a request. Include the table, token, tombstone count, and queue depth. Do not log the raw partition key.
- Do not flush memtables. The request compacts only existing SSTables that may contain the partition, and each selected SSTable is rewritten in full.

## Assumptions

- `tombstone_compaction_queue_capacity` applies node-wide across all keyspaces and tables. YAML supplies the restart value. JMX and virtual-table updates change only the running process and do not rewrite `cassandra.yaml`.
- The trigger uses the existing strict threshold behavior: enqueue on the first read-side purge count greater than `tombstone_warn_threshold`, not when the count is equal to it.
- Each replica makes an independent local decision. This feature does not coordinate queue contents across replicas.
- The feature does not force a repair or a memtable flush. Standard compaction safety checks can retain a candidate tombstone if the state changes or an overlapping SSTable or memtable still requires it.

## Risks and Mitigations

- **Write amplification and latency:** A key-targeted request rewrites whole SSTables that may contain the key. Limit work to one dedicated thread, cap outstanding requests, use the normal compaction rate limiter, and make the warning explain that the trigger is a fallback. Detect impact through existing active-compaction and bytes-compacted metrics.
- **Zombie data:** Earlier scheduling can purge a tombstone soon after it becomes eligible. Never ignore `gc_grace_seconds`, repaired-only mode, overlap checks, or memtable checks. Document that repair must still meet the table's grace-period assumptions.
- **Repair interference:** A forced major compaction has higher priority and can cancel other work. Mark reactive tasks as `TOMBSTONE_COMPACTION`; keep busy requests queued until anti-compaction or validation releases the table. The anti-compaction regression test detects priority or cancellation regressions.
- **Read-path overhead:** Per-cell recounting could add measurable CPU cost. Count only successful decisions inside the existing purge traversal and do not enable the optional cell-granularity metric. Compare focused read tests before and after if benchmark infrastructure is available.
- **Queue churn or read blocking:** Executor queue limits use a blocking rejection policy. Admit under the manager lock, submit only one drain worker, and reject full queues immediately. Keep identity membership while a request is active or requeued.
- **Runtime resize ambiguity:** Lowering a limit below current occupancy can otherwise imply cancellation. Define the setter as an admission-only change, keep accepted work, and test increase, decrease, and zero transitions through both JMX and CQL.
- **Virtual-table mutation scope:** Making all settings writable would create a broad and unsafe configuration API. Allowlist only `tombstone_compaction_queue_capacity`, route it through the validated setter, preserve read-only failures for every other row, and rely on existing virtual-table authorization.
- **Cursor compatibility:** Cursor compaction is selected globally and only for supported inputs. Reuse `CompactionTask` and `AbstractCompactionPipeline.create()` instead of constructing a pipeline directly, and assert both cursor selection and iterator fallback.
- **Stale schema work:** A table can be dropped while a request waits. Store its table ID, resolve it at execution, and discard the request if that ID no longer exists.
- **Head-of-line delay:** Repair or another compaction can hold one table for a long time. Move busy requests to the FIFO tail with a fixed retry delay so unrelated queued partitions can progress without busy-spinning.
