Where SRP Meets Tombstone Paging

Short Read Protection assumes that replica limits explain an underfilled source. Graceful tombstone paging introduces a second explanation: the replica deliberately stopped its scan with more content still reachable. The current branch stores that explanation on the replica command and omits it from the response contract.

The semantic collision

Two correct local decisions need one shared completion model.

Each feature solves a different source of read underfill. Their composition turns a local stopping optimization into coordinator-visible state.

Coordinator contract

Short Read Protection completes replica streams.

A replica that filled its command limit may have more rows. Reconciliation can discard some returned rows through newer tombstones, liveness, or filtering. SRP resumes that exact replica after its last observed clustering or partition key.

  • Per-source counters observe the replica before reconciliation.
  • A merged counter observes final live output.
  • An underfilled retry means natural exhaustion when it returns fewer rows than requested.
ShortReadProtection.java:30-82 · ShortReadRowsProtection.java:76-171
Replica contract

Graceful tombstone paging bounds one scan.

A configured replica stops a row iterator after the tombstone failure count is exceeded. It records the current row so a pager can resume beyond that clustering on another command.

  • The response can contain fewer live rows than requested.
  • More live rows and reconciliation tombstones may remain in storage.
  • The stop reason and stopping row live on the replica command.
ReadCommand.java:650-780 · AbstractQueryPager.java:219-275
Shared implication: SRP interprets a short source response as exhaustion. Graceful tombstone paging can produce the same response shape as an intentional checkpoint. A response completion field must make those states distinguishable.

Concrete composition

An SRP refill reaches a tombstone checkpoint.

This sequence follows the current source control flow. The final user-visible truncation remains a high-confidence static inference pending a focused distributed reproducer.

Replica A fills the original limit

For a page limit of 2, A returns live rows c1 and c2. More content follows on A.

Replica B supplies a newer delete

B returns a tombstone for c1. Reconciliation removes that row, leaving one live row in the merged page.

SRP resumes A after c2

The source had filled its original command and the merged counter remains hungry. ShortReadRowsProtection sends a CL.ONE child read to A.

A crosses the tombstone failure threshold

The child command encounters F + 1 tombstones before the next live row cN. Graceful mode stops and stores its local stopping row.

The response omits the completion reason

ReadResponse carries the shortened unfiltered payload. Its data may include the checkpoint row, with no field designating that row as a checkpoint. The child command and its tombstoneLimitedRow stay in the replica process.

SRP classifies the source as consumed

The retry returned fewer rows than lastQueried. ShortReadRowsProtection.moreContents() returns null on the next extension check.

Result-size inference

The client page can finish short.

The merged counter remains below its target and SRP has no continuation signal for A. The outer pager sees an ordinary short result.

Reconciliation inference

A later tombstone can remain unseen.

A continuation may contain a tombstone needed to suppress older data from another replica. Premature source completion can expose that older row.

The reconciliation risk follows an explicit SRP design requirement: continuation content may carry tombstones that shadow rows or partitions returned by another source. Runtime confirmation should assert both result cardinality and row contents.

Mixed configuration

Replicas can terminate differently

An old or disabled replica throws TOE at F + 1. An enabled replica returns a shortened success response with the same wire shape as natural exhaustion.

Adjacent read-path surfaces

The completion state propagates beyond ordinary row refill.

Design requirements

Align the response contract before enabling the feature.

The smallest durable model carries completion reason, progress, and continuation ownership through every layer that can consume an under-limit response.

Name replica completion explicitly

A response must distinguish natural exhaustion, row-limit exhaustion, tombstone checkpoint, cancellation, and any future bounded-scan state that permits more content.

Carry a complete resume position

Single-partition and range reads need direction-aware clustering, partition identity, and exclusivity. Range tombstone boundaries need a stream-safe representation.

Let SRP consume replica completion

A tombstone checkpoint should trigger another exact-source child read under the original deadline. It must avoid the natural-exhaustion shortcuts in row and partition protection.

Preserve reconciliation placement

Continuation payloads stay unfiltered until they re-enter the outer merge, read-repair listener, liveness filtering, RFP, and final counter.

Keep protocol paging as the outer cursor

The client receives a page only after coordinator source completion reaches a stable page boundary. Empty pages still require guaranteed forward progress and a bounded request policy.

Negotiate mixed-version behavior

A capability or version rule must prevent semantic disagreement between peers that throw TOE and peers that emit checkpointed responses.

Proposed invariant

Every incomplete replica response carries enough state to continue that source exactly once.

The coordinator retains ownership of reconciliation and final page completeness. The replica retains ownership of scan safety. Explicit completion metadata joins those responsibilities without moving either feature out of its natural layer.
